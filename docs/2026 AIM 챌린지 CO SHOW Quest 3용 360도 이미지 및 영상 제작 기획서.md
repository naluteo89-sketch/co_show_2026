**작성일 2026년 10월 20일 · 기획 초안 v1.0 · 2026 AIM 챌린지 CO-SHOW**

# 전시 콘텐츠와 제작 범위

## 체험 콘셉트

**제안 콘셉트는 AI로 만든 움직이는 공간에 들어가는 경험이다.** 첫 장면은 숲, 정원 또는 빛이 흐르는 공간처럼 큰 형태가 명확하고 느린 움직임이 어울리는 환경으로 선정한다. 관람자의 가상 카메라는 고정하고, 구름·물결·나뭇잎·빛 입자 등의 변화를 중심으로 공간에 생동감을 준다.

얼굴, 글자, 촘촘한 격자, 가까운 물체는 생성 오류가 쉽게 드러나므로 첫 제작에서는 비중을 낮춘다. 전시 제목과 설명은 파노라마에 직접 굽기보다 Unity UI로 표시하여 읽기 쉽게 유지한다.

관람자는 착용 안내와 정면 맞추기를 거쳐 60\~90초 안에 핵심 장면을 경험한다. 첫 영상은 10\~20초 분량의 반복 가능한 결과물로 제안한다. 모델이 지원하는 짧은 클립부터 검증하고, 연결부 검수 후 길이를 늘린다. 전시 운영 시에는 영상 반복과 다른 이미지 감상을 조합한다.

## 일반 360도 콘텐츠와 Quest 3용 콘텐츠의 차이

Quest 3 전용 제작은 새로운 이미지 파일 형식을 뜻하지 않는다. 동일한 등장방형 투영인 ERP를 사용할 수 있지만, 실제 헤드셋에서의 선명도·이음새·재생 성능·편안함을 기준으로 검수해야 한다. Quest 3의 디스플레이는 눈당 2064×2208이며, 이 수치와 전체 파노라마 파일 해상도는 서로 다른 기준이다. [Meta 공식 Quest 3 소개](https://about.fb.com/news/2023/09/meet-meta-quest-3-mixed-reality-headset/)

| 구분 | 모노 360도 | 스테레오 360도 |
| - | - | - |
| 눈에 제공하는 영상 | 양안에 같은 파노라마 | 왼눈·오른눈용 파노라마 각각 제공 |
| 깊이 단서 | 원근·크기·가림 등 단안 단서 | 단안 단서와 양안 시차 |
| 예시 규격 | 4096×2048, 2:1 | 눈당 4096×2048을 상하로 배치하면 4096×4096 |
| 검수 난도 | 이음새와 구면 형상 중심 | 눈별 정합성·시차·피로도까지 추가 |
| 이번 프로젝트 | 필수 제작 범위 | 후속 실험 범위 |

상하 배열은 스테레오 저장 방식 중 하나이며 좌우 배열도 가능하다. 단순히 같은 이미지를 두 번 배치하면 입체 정보가 생기지 않는다. Unity는 스테레오 파노라마의 눈별 영상을 분리해 표시하는 구성을 제공한다. [Unity 스테레오 파노라마](https://docs.unity3d.com/6000.0/Documentation/Manual/VideoPanoramic-3D.html)

모노도 주변을 둘러보는 몰입형 경험을 제공한다. 다만 모노와 스테레오 파노라마 모두 일반적인 고정 시점 재생만으로는 관람자가 몸을 옮겨 물체 뒤를 보는 자유 이동을 제공하지 않는다. 6DoF 공간 탐색은 별도의 3D 제작 과제로 분리한다.

## 최종 납품물

- 360도 정지 이미지 3장: 생성 원본, 보정본, 최종본을 구분하여 보관한다.

- 360도 영상 1편: 최종 재생본과 압축 전 마스터를 함께 보관한다.

- Quest 3용 Unity 프로젝트 및 APK: 오프라인 실행, 반복 재생, 정면 맞추기, 대체 이미지 전환을 포함한다.

- ComfyUI 워크플로 JSON 및 실험 기록: 모델·LoRA·노드 버전, 프롬프트, 시드, 주요 값을 남긴다.

- 전시 운영 안내: 실행·종료·복구 순서와 콘텐츠 교체 방법을 정리한다.

# 화질 목표와 기술 기준

## HD와 4K 목표를 측정 가능한 기준으로 전환

사용자의 ‘HD 한계 화질 또는 4K에 최대한 가까운 사진’ 목표는 **파일 크기 확대와 실제 디테일 개선을 나누어 평가**한다. 4K 파노라마가 일반 4K 화면과 같은 선명도를 낸다고 약속하지 않는다.

| 단계 | 정지 이미지 | 영상 | 판정 목적 |
| - | - | - | - |
| 구조 검증 | 모델에 맞는 2:1 저해상도 | 모델 기본 해상도와 짧은 길이 | 공간 구성·경계·움직임 검증 |
| 1차 납품 후보 | 4096×2048 | 4096×2048, 24 또는 30fps | 전시용 최소 목표와 실기기 검수 |
| 화질 개선 후보 | 6144×3072, 8192×4096 비교 | 6K 이상은 디코딩 성능 확인 후 선택 | 실제 시야 디테일 개선 여부 |
| 최종 선택 | 실기기에서 더 선명한 파일 | 선명도와 안정성을 함께 통과한 파일 | 크기만 큰 결과물 제외 |

위 규격은 이 프로젝트의 제안 목표다. 모델의 생성 해상도와 업스케일된 납품 해상도를 실험 기록에서 분리한다. 8K는 도전 목표이며 정지 이미지의 재생 성공이 동일 해상도 영상의 재생 성공을 보장하지 않는다.

## 360도로 만들면 흐릿해지는 이유

가장 큰 이유는 전체 픽셀이 화면 한 장면이 아니라 **360도 전 방향에 나뉘어 배정되기 때문**이다. ERP 가로 폭을 W라고 할 때, 적도 부근 90도 구간에는 약 W÷4개의 가로 샘플이 들어간다.

| 전체 ERP 크기 | 90도 구간의 가로 샘플 수 |
| - | - |
| 1920×960 | 약 480 |
| 4096×2048 | 약 1024 |
| 6144×3072 | 약 1536 |
| 8192×4096 | 약 2048 |

이는 각도에 따른 단순 계산이며, 렌즈·화면 해상도·리샘플링·압축을 반영한 실제 시야 해상도는 아니다. 예를 들어 4K 파노라마를 헤드셋에서 보면 한 번에 보는 영역에는 전체 4K 중 일부만 사용된다.

ERP는 위도와 경도를 직사각형으로 표현하므로 극점 부근의 픽셀 배분이 비효율적이고, 일반 평면 이미지 모델이 다루기 어려운 왜곡이 생긴다. 그러나 ERP 변환 자체가 언제나 전체 화면을 저화질로 만드는 것은 아니다. 출력 크기, 투영 방식과 리샘플링 횟수에 따라 손실이 달라진다. 파노라마 생성 연구에서도 투영 왜곡과 구면 경계의 일관성을 주요 문제로 다룬다. [SphereDiff 연구](https://arxiv.org/abs/2504.14396)

실제 작업에서는 다음 손실을 따로 확인한다.

1. **원본 범위 부족:** 일반 사진 한 장에 없는 뒤쪽·천장·바닥은 생성하거나 추가 촬영해야 한다. 단순히 가로로 늘리는 방식으로는 완성된 360 공간을 얻을 수 없다.

2. **생성 단계의 디테일 부족:** 낮은 해상도에서 만든 질감과 구조는 나중에 크기만 늘려도 원본처럼 복원되지 않는다.

3. **반복 변환과 재생성:** 축소·확대, 투영 변환, 강한 denoise를 반복하면 선명도와 형태가 달라질 수 있다.

4. **영상의 시간축 오류:** 프레임마다 디테일이 달라지면 깜빡임과 표면이 끓는 듯한 현상이 발생한다.

5. **압축 및 재생 설정:** 낮은 비트레이트, 색상 변환, Unity의 실제 텍스처·렌더 해상도가 최종 화질에 영향을 준다.

최종 평가는 원본·보정본·영상 프레임을 같은 방향과 시야각에서 비교한다. 정면뿐 아니라 좌우 경계, 뒤쪽, 천장과 바닥을 확인한다.

# LoRA 및 노드 실험

## 학습과 제작을 연결하는 방식

현재 test.json에는 모델·LoRA 로더, 텍스트 조건, KSampler, VAE, 이미지 크롭·마스크·합성·스케일 노드가 포함되어 있다. 이를 이미지 실험의 출발점으로 사용한다. 영상 모델은 로더와 조건 입력 구조가 다를 수 있으므로 기존 이미지 그래프에 그대로 교체하지 않고, 해당 모델의 공식 예제 워크플로에서 별도로 시작한다.

| 학습 순서 | 이해할 내용 | 제작에 적용할 결과 |
| - | - | - |
| 모델과 조건 입력 | UNET·CLIP·VAE의 역할, 프롬프트와 시드 | 동일 조건의 기준 이미지 |
| LoRA 적용 | 베이스 모델 호환성, 가중치, 트리거 | 구면 구조와 스타일 변화 비교 |
| 샘플링 | steps·CFG·sampler·denoise | 형태 유지와 디테일의 균형 |
| 이미지 보정 | 크롭·마스크·합성·타일·업스케일 | 이음새와 국부 손상 개선 |
| 영상화 | 프레임 수·fps·조건 입력·시간 일관성 | 움직이는 360도 시험 클립 |
| 출력과 검수 | 인코딩·Unity 재생·기기 성능 | 최종 전시 후보 |

## 실험 1 LoRA 조정으로 무엇이 변하는가

프롬프트·시드·모델·출력 크기를 고정하고 LoRA 강도만 변경한다. 예를 들어 0, 0.5, 0.8, 1.0을 초기 비교값으로 사용할 수 있으나, 해당 LoRA가 권장하는 범위와 로더 구조에 맞춘다. 이 값들은 최적값이 아니라 실험 출발점이다.

관찰 항목은 파노라마 구조, 수평선, 좌우 연결, 천장·바닥, 사물 비율, 색감·스타일, 질감 과장이다. 효과가 강해질수록 품질도 좋아진다고 가정하지 않는다. 형태 변형과 경계 오류를 줄이면서 필요한 효과를 얻는 값을 고른다.

## 실험 2 노드 조정으로 화질을 개선할 수 있는가

기준 출력과 다음 세 경로를 비교한다.

| 경로 | 변경 내용 | 확인할 점 |
| - | - | - |
| A | 단순 이미지 확대 | 픽셀 수 증가와 실제 디테일 차이 |
| B | 전용 업스케일 모델 | 경계선·노이즈·질감 보존 |
| C | 업스케일 후 낮은 denoise의 부분 보정 | 디테일 개선과 구조 변형의 균형 |

추가로 seam-aware 처리의 켜기·끄기를 비교한다. 좌우 경계는 화면의 중앙으로 옮겨 보정한 뒤 원래 방향으로 복원하는 방식을 시험할 수 있다. 타일 업스케일은 타일 사이와 0도·360도 경계가 함께 맞아야 한다. Seamless 노드 팩은 원형 VAE 패딩, latent roll, 구면 위치 처리 등을 제공하지만 움직이는 카메라에서 형태 변형과 극점 문제가 남을 수 있다. [ComfyUI-Seamless-Equirectangular](https://github.com/Burgstall-labs/ComfyUI-Seamless-Equirectangular)

## 실험 기록과 채택 기준

대표 장면 1개에서 각 변수를 따로 비교한 후, 선택한 설정을 3개 시드로 재검증한다. 마지막에는 다른 성격의 장면 2개에 적용해 특정 샘플에만 맞는 설정인지 확인한다.

기록 항목은 모델·LoRA 파일명과 버전, 노드 커밋, 프롬프트, 시드, 해상도, 강도, steps, CFG, denoise, 생성 시간, 최대 VRAM, 오류와 Quest 3 평가다. 사용하지 않는 항목은 해당 없음으로 표시한다. 선명도·구면 연결·형태 보존을 각 5점 척도로 비교하고, 영상에는 시간 일관성을 추가한다. 재현 가능한 개선이 확인된 설정만 다음 단계로 넘긴다.

| - | - | - |
| 360도 이미지 기반 영상화 | 장면을 유지하며 구름·물결 등의 움직임 생성 | 우선 실험. 파노라마 조건 유지 여부를 먼저 판정 |
| 일반 영상의 360도 아웃페인팅 | 입력 시야 밖을 생성해 전체 구면으로 확장 | 이미지 기반 경로가 불안정할 때 비교 |
| 텍스트에서 360도 영상 생성 | 원하는 공간을 직접 영상으로 생성 | 원본 이미지 일치보다 공간 연출이 중요할 때 비교 |
| Unity에서 정지 파노라마와 움직임 합성 | 배경에 파티클·조명·오브젝트를 더함 | AI 영상 품질이 미달할 때 전시 대안 |

마지막 경로는 실시간 체험 방식이므로 단일 360도 동영상 파일이 필요하면 별도의 구면 렌더링·녹화 단계를 추가한다. 정지 파노라마를 회전시키기만 하는 연출은 ‘환경이 움직이는 영상’의 완료 기준으로 삼지 않는다.

- **ComfyUI-Tutu-360VR-Tools:** 360도 영상 워크플로와 대형 출력 후처리의 비교 후보로 둔다. 8K 출력 파일을 얻는 것과 8K 원본 디테일을 확보하는 것은 별도로 평가한다. [저장소](https://github.com/zhaotututu/ComfyUI-Tutu-360VR-Tools)

- **WAN 2.2 360Rotation 및 MiniMax H3 360 Orbit:** 피사체 회전 또는 카메라 공전 영상용이다. 주변 전체가 동시에 담긴 ERP 영상과 목적이 다르므로 이번 360 공간 제작의 기본 경로에서 제외하고, 필요 시 평면 홍보 영상에 활용한다. [WAN 모델 카드](https://huggingface.co/artificialguybr/360Rotation-Redmond-WAN2-I2V-14B) · [MiniMax 모델 카드](https://huggingface.co/pablodawson/MiniMax-H3-360-Orbit-LoRA)

## 영상 품질 검수

카메라는 고정하고 움직임의 크기를 작게 시작한다. 좌우 경계에 걸친 물체의 위치·형태·색이 시간에 따라 연결되는지 확인한다. 천장·바닥의 뒤틀림, 프레임 간 밝기 변화, 오브젝트의 생성·소멸도 함께 검사한다.

이음새를 중앙으로 이동한 후 VACE 계열 인페인팅으로 수선하는 방식은 추가 실험 후보로 둔다. 수선 결과의 색감과 시간 일관성을 원본과 비교하여 채택한다. 미리보기 도구는 중간 검수에 사용하고 최종 판정은 Unity 앱을 설치한 Quest 3에서 수행한다.

영상의 첫 프레임과 마지막 프레임이 같더라도 자연스러운 루프가 자동으로 보장되지는 않는다. 움직임의 방향·속도와 오디오 연결까지 반복 재생으로 검사한다. 프레임별 독립 생성형 업스케일은 깜빡임이 늘어날 수 있어 시간축 안정성을 우선한다.

## 현재 Unity 프로젝트의 확장

현재 Pano360Viewer는 Texture2D 기반 이미지 뷰어이며 전용 스크립트에서 VideoPlayer 연결은 확인되지 않았다. 다음 영상 기능을 추가 개발한다.

1. **재생 경로:** VideoPlayer → RenderTexture → 기존 ERP 머티리얼로 연결한다. Unity가 안내하는 파노라마 영상 구성에 맞춰 영상과 텍스처 크기를 정하고, 기존 셰이더에서 방향·상하 반전·색상 처리를 검증한다. [Unity 파노라마 영상 설정](https://docs.unity3d.com/6000.0/Documentation/Manual/VideoPanoramic-setup.html)

2. **콘텐츠 관리:** 이미지·영상 목록, 형식, 해상도, 모노·스테레오 레이아웃을 구분한다.

3. **재생 제어:** 준비 완료 후 시작, 재생·정지, 다음·이전, 반복, 정면 맞추기를 구현한다.

4. **오류 복구:** 로딩 안내, 디코딩 오류 시 대체 이미지 표시, 운영자 재시작 기능을 구현한다.

5. **전시 운영:** 기기 내부 파일로 오프라인 재생하고, 헤드셋 착탈·절전 복귀 후 상태를 검사한다.

초기 인코딩 시험은 MP4의 H.264와 HEVC를 후보로 두고 4K·24/30fps에서 시작한다. 비트레이트는 20·40·60Mbps를 비교 출발점으로 삼되, 지원 여부와 최적값은 실제 Unity APK에서 결정한다. 동일 파일의 브라우저 재생 결과만으로 앱 성능을 판정하지 않는다.

영상 fps와 VR 앱의 표시 주사율은 분리한다. 24/30fps 영상이어도 고개 회전에 따른 화면 갱신은 앱이 안정적으로 처리해야 한다. 프로젝트의 주사율 목표를 정하고 해당 프레임 예산을 측정한다.

## 필요한 자원과 판단 시점

제작에는 ComfyUI 실행 PC와 GPU, Quest 3, Unity Android 빌드 환경, USB 연결, 원본·캐시·마스터를 저장할 공간이 필요하다. GPU와 VRAM, 사용 가능한 인원·예산은 첫 주에 확정한다. ‘RTX 4090에서 15분, VRAM 20GB와 공유 메모리 30GB’라는 메모는 재현 조건이 확인되지 않은 참고치로만 두고 제작 일정이나 장비 구매의 기준으로 사용하지 않는다.

역할은 콘텐츠·ComfyUI 제작, Unity 통합, 실기기 검수·전시 운영으로 구분하되 인원이 적으면 겸임한다. 비용은 모델 이용 조건, 외부 GPU 사용 여부와 실측 생성 시간, 저장장치·운영 소모품을 확인한 뒤 산정한다.

첫 주 말에는 4K 시험 영상 재생과 생성 소요 시간을 확인한다. 둘째 주 말까지 360도 영상의 구조가 안정되지 않으면 장면 움직임을 줄이거나 Outpaint·Unity 합성 경로로 전환한다. 마지막 주에는 모델과 노드 버전을 고정하고 오류 수정과 운영 검수에 집중한다.

## 제작 근거와 관리

프로젝트 현황은 로컬 Pano360Viewer README, ProjectVersion.txt, Runtime 스크립트와 test.json의 구성에 근거한다. 실행 파일과 생성 결과의 최종 품질 판정은 위 검수 단계에서 수행한다.

기술 출처는 본문 각 항목에 연결한 Meta·Unity 공식 문서, 모델 작성자의 Hugging Face 카드, 노드 제작자의 GitHub 저장소다. 설치 시 실제로 사용한 모델 파일과 노드 버전을 실험표에 고정하여 업데이트 이후에도 결과를 재현할 수 있게 한다.

**첫 실행 과제:** 기존 이미지 1장을 기준본으로 선정하고, LoRA 강도 비교표와 4K 시험 영상을 준비한다. 같은 주에 Quest 3 앱에서 영상 재생을 확인해 생성 품질과 재생 성능을 함께 판단한다.
